# deferredrequest

Сервис по функционалу похож на executor: через определенное время делает GET POST запросы, но квант времени миллисекунда (фактически 10 миллисек). Кроме того явно указывается полный URI: сервис будет более гибким в использовании.


Сервис в отличие от executor хранит задачи не в базе, а во внутренней памяти. Раз в 10 сек он проверяет есть ли изменения, и если да то сбрасывает список задач в локальный файл, если была указана соответвующая опция при запуске. При старте читает этот список задачи из файла, если была указанна соответвующая опция. То есть сервер работает в режиме STATE FULL.


Сервис принимает задачи по http ну и сам делает http/https GET/POST запросы, никакой спец защиты у сервиса нет, поэтому нужно правильным образом распологать его всетевой инфраструктуре.

Вот GET запросы на которые он реагирует
[/name/SomeName]/put/**timeout**?uri=escaped_full_uri    где **timeout** таймаут в секундах
[/name/SomeName]/put/**timeout**ms?uri=escaped_full_uri    где **timeout** таймаут в миллисекундах
[/name/SomeName]/put/**timeout**s?uri=escaped_full_uri    где **timeout** таймаут в секундах
[/name/SomeName]/put/**timeout**min?uri=escaped_full_uri    где **timeout** таймаут в минутах
[/name/SomeName]/put/**timeout**h?uri=escaped_full_uri    где **timeout** таймаут в часах
Кроме того может реагировать на POST запросы при этом требутся чтобы был параметр uri который удаляется из запроса при каллбеке

Для rest калбеков нужно чтобы урл был передан как часть path, а переданный body должен быть читаемой строкой
[/name/SomeName]/rest/**timeout**/base64_full_uri    где **timeout** таймаут в секундах
[/name/SomeName]/rest/**timeout**ms/base64_full_uri    где **timeout** таймаут в миллисекундах
[/name/SomeName]/rest/**timeout**s/base64_full_uri    где **timeout** таймаут в секундах
[/name/SomeName]/rest/**timeout**min/base64_full_uri    где **timeout** таймаут в минутах
[/name/SomeName]/rest/**timeout**h/base64_full_uri    где **timeout** таймаут в часах

Для бинарных rest калбеков нужно чтобы урл был передан как часть path, а переданный body может быть любым байтовым массивом
[/name/SomeName]/rest/**timeout**/base64_full_uri    где **timeout** таймаут в секундах
[/name/SomeName]/rest/**timeout**ms/base64_full_uri    где **timeout** таймаут в миллисекундах
[/name/SomeName]/rest/**timeout**s/base64_full_uri    где **timeout** таймаут в секундах
[/name/SomeName]/rest/**timeout**min/base64_full_uri    где **timeout** таймаут в минутах
[/name/SomeName]/rest/**timeout**h/base64_full_uri    где **timeout** таймаут в часах

Для /rest/ и /bin/ запросов может быть дополнительно переданны заголовки они должны начинаться с с префиксов X-Replace- или x-replace-
эти префиксы затем удаляются при совершении rest запроса, пример:
curl -X POST -H 'X-Replace-Content-Type: application/json' -d '{"id":"1683214968","jsonrpc":"2.0","method":"VideoCall/Sum","params":{"a":1,"b":2}}' "http://127.0.0.1:1122/rest/10s/aHR0cDovLzEyNy4wLjAuMTo4Mjgy"

uri = это заэскепленный uri для вызова через заданный timeout. В выше описанном способе будет сделан GET запрос. Для POST запроса параметры для deferredrequest должны быть перданы через POST, но кроме того должен быть еще параметр или несколько помимо uri.

Если есть [/name/SomeName] в самом начале path то это именованная задача. Она не будет имееть Id, но у нее есть Name. После выполнения она снова будет поворяться через указанный таймаут времени, т.е. таймаут в данном случае это минимум между запросами. Это сделанно для тяжелых задач чтобы не забить сервер заведомо тяжелыми задачами и гарантированно дать время между задачами.

На выполнение задачи / запроса выдается время TIMEQUANTUMWAIT = 20 сек. После сервер НЕ ЖДЕТ ответа и закрывает соединение. Для обычных задач это не очень важно - главное инициализация какого то действи, а потом оно может длиться минуты, ответ обычно никому не нужен, этому сервису тоже. Для именованных задач это может быть проблемой, так как после ожидания задача снова ставиться в очередь на выполнение. И чтобы не забить сервер сложными задачами нужно гарантированно завершать их за TIMEQUANTUMWAIT сек, время можно увеличить, но нужно быть уверенными что возможный прокси сервер (nginx) не оборвет висящий в ожидании запрос от deferredrequest сервера.

Возвращается json описание объекта задача, если нет errno то все хорошо. задача имеет id - идентификатор
{"data":{"id":1,"created":"2021-08-19T14:35:40.436340518+03:00","timeout":"2021-08-19T14:35:52.436340518+03:00","uri":"http://dbirykov.dev2.loveplanet.ru/api/a-geo?type=1"}}

Кроме постановки задачи можно ее удалить вызовом
/del/id             где id идентификатор который был указан при постановке задачи
/name/SomeName/del  где SomeName имя именованной задачи

Есть метод выборки задачи
/get/id             где id идентификатор который был указан при постановке задачи
/name/SomeName/get  где SomeName имя именованной задачи

Ну и сугубо справочный метод, по выборке списка задачи, задачи тут отсортированны по времени выполнения, внимание именованные задачи в процессе выполнения будут сдвигаться в очереди вправо на время TIMEQUANTUMWAIT * 2 от их привычного duration. а после выполнения заниматься место согласно duration
/list?limit=10&offset=0

Запуск
./deferredrequest -h
Usage of ./deferredrequest:
  -addr string
      server bind addres (default ":1122")
  -maxproc int
      maximum process (default 17)
  -store string
      store file
  -verb int
      verbocity
пример
./deferredrequest -addr :8181 -store tasts.json.log
путь к файлу может быть относительным или абсолютным
